    Sans clé, tout tourne dans votre navigateur, sans modèle. Avec une clé, la génération part vers votre point d'accès compatible OpenAI, avec le même prompt et le même schéma JSON que le code Python ; la clé reste dans la session de cet onglet (sessionStorage) et n'est envoyée qu'au fournisseur.

    Comment ça marche

    Ce chatbot documentaire suit la série Enterprise Document Intelligence (Towards Data Science, 2026) : quatre briques, des contrats typés entre elles, et ce qu'une brique passe à la suivante est ce qui est enregistré. Il n'y a ni base vectorielle, ni framework, ni agent ; le modèle est optionnel sur chaque chemin, et par défaut il n'y en a pas.

    Les quatre briques

    1. Le guide devient des tables. Le site est lu une fois, puis seules les tables servent : page_df (une ligne par page), line_df (chaque bloc visible, numéroté : l'unité de citation), toc_df (les titres avec leurs bornes de lignes), row_df (les lignes de tableaux), cross_ref_df (les liens internes), corpus_index (une ligne par page, écrite pour le routeur). Articles : Stop Returning Flat Text from a PDF: The Relational Tables RAG Needs, Beyond extract_text, Multi-Document RAG: A Folder of Unrelated PDFs Is One Long Document with a Nested Outline.
    2. La question devient une ligne typée avant toute recherche. ParsedQuestion : la question corrigée contre le vocabulaire du corpus (jamais contre un modèle), les mots-clés avec leur origine (direct, expert_dictionary, anchor), la forme de la réponse (une valeur ou une liste), son type (texte, montant, date, oui/non, durée…), la page lue, la décomposition « et », et au besoin une clarification unique avec un défaut proposé. Puis un dispatcher déterministe écrit un ExecutionPlan : chaque méthode activée ou non, avec sa raison. Articles : Parse the question before you search, Five fields RAG should extract from any question, Dispatching the Parsed RAG Question, Noisy Text in RAG, When RAG Users Ask Vague Questions: Clarify Once, Learn the Default.
    3. La recherche est un filtrage, pas une recherche. Le routeur choisit une à trois pages (le sommaire du corpus), puis descend dans leur plan. Des détecteurs par mots-clés tournent toujours (mots entiers, accents repliés, co-occurrence), les titres sont un signal de premier rang, les motifs typés (montant, date, téléphone) sont exigés quand la question les demande ; les embeddings sont absents et la raison est consignée. L'ancre (les lignes touchées) est petite, le contexte (le paragraphe ou la section) est grand et contient toujours l'ancre. Un arbitre déterministe donne à chaque candidat un rôle (primary, supporting, tangential, discarded) et une phrase de raison. Un balayage exhaustif de toutes les pages prouve l'absence. Articles : Retrieval Is Filtering, Not Search, Finding the Right Anchor Is Where RAG Stops Hallucinating, An LLM as arbiter in RAG retrieval, 6 common RAG retrieval mistakes.
    4. La génération remplit un schéma typé, jamais de la prose libre. Des items avec leurs spans (doc_id, line_start, line_end, citation), deux booléens (answer_found, complete_answer_found), des réserves. Sans modèle, le code recopie les lignes de l'ancre (verbatim) ou la valeur capturée (computed). Un validateur vérifie chaque span et chaque citation avant l'affichage ; ce qui échoue n'est pas montré. « Pas dans ce guide » apporte quatre preuves : la couverture de l'index, les concepts cherchés avec leurs variantes et leurs comptes, le balayage, les mentions les plus proches avec la raison pour laquelle elles ne répondent pas. Articles : Stop Returning Text from RAG: The Typed Answer Contract, Validating the RAG Answer Before the User Sees It, A RAG That Says “Not in This Document” Has to Show Four Kinds of Evidence, Prompt engineering for RAG generation.

    Le plan

    Le dépôt public SFHAJJI/guide-rag tient le paquet Python (le pipeline de référence : guide_rag/parsing, question, retrieval, generation), l'index construit (index/*.json), le dictionnaire expert en YAML, le jeu d'évaluation étiqueté par type, et cette page. Le navigateur exécute un port JavaScript des briques déterministes 2 à 4 (web/engine/*.js, un module par fichier Python, mêmes noms de fonctions) ; un test croisé (tests/test_crosscheck.py) fait tourner les questions du jeu d'évaluation dans les deux et exige les mêmes mots-clés, les mêmes pages, les mêmes candidats et rôles, les mêmes spans et le même verdict.

    Ce qui n'est délibérément pas là : pas de base vectorielle (le guide est petit, son vocabulaire est couvert par le dictionnaire, et un zéro de mot-clé est une absence honnête) ; pas d'agent (chaque route est une règle lisible dans dispatcher.py) ; pas de modèle sur le chemin par défaut.

    Évaluation

    Le jeu d'évaluation est étiqueté par type de question (factuelle, liste, montant, date, oui/non, coquille, anglais, allemand, sur la page lue, composée, vague, hors du guide). Les résultats sont lus dans eval/report.json, écrit par guide-rag eval.
